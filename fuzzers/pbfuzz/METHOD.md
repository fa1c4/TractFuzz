# PBFuzz method and comparison boundary

The standalone author run uses `/pbfuzz run <campaign.yaml>` in pinned DSH. The model writes semantic bug predicates, preconditions, root causes and trigger plans (PLAN), implements a Python property-based input generator (IMPLEMENT), runs the generator and oracle (EXECUTE), then decides whether to stop or revise (REFLECT). The engine records hypotheses, generator code, input files, per-iteration metrics and a terminal PoV in `state/`. The current protocol is in `packages/dsh-pbfuzz/src/core/fsm.ts`, `tools.ts`, and the schemas under `contracts/` in the pinned checkout; the archived protocol and prompt template are in `pbfuzz_source/prompt.py` in the Zenodo artifact. DSH session archives retain actual prompts and tool calls.

`scripts/run_pbfuzz_magma.sh BUG_ID TARGET_NAME FIXED_PROGRAM` builds the author Magma fork, generates its campaign, and invokes the author launcher. It must receive the fixed entry from `docs/tractfuzz_magma_benchmarks.md`. The campaign provides the model with `MAGMA_LOG` source location and condition, canary patterns, source tree, and seed corpus. Static analysis is disabled because the author fork has no prebuilt KAMain outputs and kanalyzer was not installed. The current run therefore uses gdb traces and target-only deviation detection. Patch files are moved out of the Magma source tree during the author launcher and restored afterward. The patched built source still contains `MAGMA_ENABLE_FIXES` branches; the PNG runs' model traces read those branches, an information advantage that must be disclosed in any comparative analysis.

The headless DSH session recorded `workspace-write` sandbox and permission preset with an `ask` approval policy. The PBFuzz plugin's Bash guard and tamper ledger kept their author defaults. The model route used `openai-completions` with no explicit temperature or sampling override in our profile; DSH resolved those defaults. `dsh-kanalyzer` was built by the author build but not installed in the headless profile, so no LLVM analysis plugin output contributed to these campaigns. The actual prompt and tool-call sequence is preserved in each compressed `session.v4.jsonl.zstd` under `results/pbfuzz/dsh-home/sessions/`.

The 60-row audit is generated by `scripts/pbfuzz_audit.py`. The Zenodo archive has seven IDs overlapping the frozen benchmark and four with exactly matching programs: `PNG006`, `SND001`, `SQL012`, `TIF006`. `PDF002`, `SSL002`, and `XML002` use different author entries, so those archived runs are separate-harness evidence. `LUA001` and `PHP014` are outside the frozen 60. The current DSH adapter can generate campaigns for other Magma rows but each row still needs a build and an actual campaign; source availability alone is not success. `PDF020` remains in the audit and is never dropped for reachability reasons.

`scripts/pbfuzz_seed_adapter.py` optionally copies a PBFuzz-generated byte file into a specified LibAFLGo initial corpus only after validating the fixed bug/entry pair. It records generator ID, input digest, model-config digest, timestamp and destination in a separate provenance ledger. Any subsequent LibAFLGo run using those seeds is **PBFuzz + LibAFLGo**, with its agent tokens and seed generation time counted separately from AFLGo execution. The import alone is not a hybrid fuzzing result.

`scripts/run_pbfuzz_fixed.sh BUG_ID` runs the current author PBFuzz engine against one of the 60 frozen Magma binaries. `scripts/pbfuzz_fixed_campaign.py` requires the exact entry and a verified target `MAGMA_LOG` line, then generates a campaign using the existing corpus. `scripts/pbfuzz_monitor_oracle.py` executes the fixed binary through Magma's monitor and translates reached and triggered row counters into the engine's text oracle. This campaign disables gdb tracing and static deviation because the fixed binary has no compatible debugger trace in this workflow. It is a **fixed-binary monitor-oracle adaptation**, distinct from both the Zenodo Cursor artifact and the standalone author Magma build. `scripts/run_pbfuzz_60.py --track fixed --execute` attempts every frozen row, including `PDF020`; `scripts/pbfuzz_fixed_replay.py` checks each generated PoV on the frozen binary in three independent monitor runs. The earlier separate PDF020 pilot remains recorded as an interrupted attempt; the new 60-row campaign attempts it again with the common adapter.

The fixed campaign copies each row's source, binary, monitor and corpus into `results/pbfuzz/isolated/<BUG>/` and checks the copied binary hash against the frozen original. During the model session, the runner moves that bug's original `magma/work/idfuzz/<BUG>/` directory to an ignored temporary location and restores it before replay. It also launches DeepSeek Harness under Linux Landlock with file reads limited to the staged target, pinned author engine, DSH profile, model runtime, system libraries, and monitor oracle script. Earlier runs that saw previous baseline witnesses are archived under `results/pbfuzz/prior-unisolated/` or `results/pbfuzz/prior-attempts/` and rerun. The Magma source still contains `MAGMA_ENABLE_FIXES` branches and the campaign supplies the canary target location, so the information given to PBFuzz remains more specific than some other baselines.
